# خطة تحويل TAT Agency System إلى SaaS متعدد الوكالات

## القرارات المعتمدة
| الموضوع | القرار |
|---|---|
| تعدد الوكالات | قاعدة بيانات واحدة + عمود `agency_id` في كل الجداول. بيانات الإنتاج الحالية تبقى **الوكالة رقم 1**. |
| التسجيل | الـ **Super Admin** بيضيف الوكالات من لوحة منصة خاصة. لا تسجيل ذاتي ولا دفع/خطط الآن (تتضاف لاحقًا). |
| الإيميلات | SMTP عام قابل للضبط من المنصة (+ SMTP خاص لكل وكالة اختياريًا)، قوالب عربي/إنجليزي، سجل إرسال. |
| الصلاحيات | أدوار جاهزة + مصفوفة صلاحيات قابلة للتعديل لكل وكالة (عرض/إضافة/تعديل/حذف/تصدير لكل قسم)، وإمكانية أدوار مخصصة. |
| اللغات | عربي + إنجليزي (RTL/LTR تلقائي): الواجهة + الـ PDF + الإيميلات + الإشعارات. لغة لكل مستخدم + لغة افتراضية للوكالة. بيانات المستخدم (أسماء عملاء، أوصاف) تفضل كما كُتبت. |
| سجل النشاط | كل التعديلات (إضافة/تعديل/حذف) + الدخول/الخروج/فشل الدخول + تغيير الصلاحيات + التصدير + Webhooks، مع **قبل/بعد**. مدير الوكالة يشوف سجل وكالته، والـ Super Admin يشوف الكل. |
| Webhooks | صادرة لكل وكالة: أحداث قابلة للاختيار، توقيع HMAC، إعادة محاولة، سجل تسليم، زر اختبار. |
| الترتيب | مراحل — الأساس أولًا، مع backup قبل أي migration وتجربة كل مرحلة قبل التي بعدها. |

## المرحلة 1 — الأساس (تعدد الوكالات + الصلاحيات + السجل + لوحة المنصة)
1. **Migration (additive، قابل للإعادة):** جدول `agencies`، إضافة `agency_id` لكل الجداول (users, clients, invoices, expenses, collection_*, ad_budgets, services, client_services, company_settings…)، backfill كله للوكالة 1، فهارس وقيود مقيّدة بالوكالة (مثل اسم الخدمة فريد داخل الوكالة). **backup إلزامي قبل التشغيل.**
2. **عزل البيانات:** التوكن يحمل `agency_id`، middleware يحدد `req.agencyId`، وكل استعلام في كل route (clients, invoices, expenses, collection, adBudgets, services, finance, settings, jobs) يتفلتر بيه. اختبارات عزل تتأكد إن وكالة ما تشوفش بيانات التانية.
3. **الأدوار والصلاحيات:** جداول `roles` و`role_permissions`، أدوار افتراضية لكل وكالة (مدير الوكالة، محاسب، مدير حسابات، عضو للعرض فقط)، middleware `requirePermission(module, action)`، والواجهة تخفي القوائم والأزرار حسب `can()`. شاشة لتعيين الدور ولتعديل المصفوفة وإنشاء أدوار مخصصة.
4. **سجل النشاط:** جدول `audit_logs` (وكالة، مستخدم، حدث، كيان، قبل/بعد، IP، متصفح، وقت)، helper `audit()` في كل عملية كتابة، تسجيل الدخول والصلاحيات. صفحة «سجل النشاط» بفلاتر (مستخدم/كيان/تاريخ/نوع) وعرض الفرق، وتبويب نشاط لكل مستخدم.
5. **لوحة المنصة (Super Admin):** دور منصة منفصل: إنشاء/إيقاف وكالات، تحديد حد المستخدمين، إنشاء أول مدير للوكالة، عرض كل السجلات.

### حالة المرحلة 1 — ✅ منفّذة ومجرّبة على النسخة التجريبية
- **تمّ:** كل الـ routes معزولة بـ `agency_id` ومحمية بالصلاحيات ومسجّلة في `audit_logs` (بما فيها `finance.js` كله)؛ الأدوار الافتراضية + مصفوفة قابلة للتعديل + أدوار مخصصة (`/api/roles`)؛ سجل النشاط للوكالة (`/api/logs`) ولوحة المنصة (`/api/platform/agencies`, `/api/platform/logs`)؛ واجهة: الفريق والصلاحيات، سجل النشاط، إدارة المنصة، وإخفاء القوائم والأزرار حسب الصلاحية.
- **التحقق:** `npm test` (38 اختبار)، `npm run audit` (292 فحص مالي، 0 أخطاء)، و`npm run isolation` (79 فحص: وكالتان لا تشوفان بعض، حدود الأدوار، حماية المصاريف الشخصية، السجل، إيقاف وكالة).
- **انحرافات عن الخطة:** الصلاحيات مخزّنة كـ JSONB داخل `roles.permissions` (بدل جدول `role_permissions` منفصل)؛ «نشاط كل مستخدم» متاح كفلتر مستخدم في صفحة السجل (مفيش تبويب منفصل)؛ تصدير التقارير لسه مش بيتسجّل في السجل (مع الإضافات الجاية).
- **قبل التشغيل على بيانات حقيقية:** (1) `node backend/scripts/backup-json.js ./backup.json` بإعدادات قاعدة البيانات الحقيقية؛ (2) شغّل الـ backend (الـ migration بيتطبّق تلقائيًا)؛ الوكالة 1 = البيانات الحالية، ومالك المنصة = `ADMIN_EMAIL` (أو `PLATFORM_ADMIN_EMAIL`)، والأعضاء الحاليين غير المديرين بياخدوا دور «عضو» (المصاريف الشخصية مش ظاهرة لهم)؛ (3) `npm run isolation` بيعمل وكالتين تجريبيتين ويوقفهم — شغّله على نسخة تجريبية مش على الإنتاج.

## المرحلة 2 — اللغات والشاشات
- طبقة ترجمة خفيفة (`t()` + قاموس ar/en)، تبديل `dir` و`lang` تلقائيًا، واستخراج كل النصوص المكتوبة بالعربي في الصفحات (~25 ملف) لقاموس واحد.
- ترجمة قوالب الـ PDF والإيميلات والإشعارات، وتنسيق التواريخ والأرقام حسب اللغة.
- مراجعة تجاوب كل الصفحات والنوافذ على الكمبيوتر والتابلت والموبايل وتوحيد النوافذ (modals) بالستايل الجديد.

### حالة المرحلة 2 — ✅ منفّذة ومجرّبة على النسخة التجريبية
- **اللغات:** `frontend/src/i18n` — الدالة `t("نص عربي")` (النص العربي هو المفتاح) والقاموس الإنجليزي في `en.part1/2/3.js`؛ لو ترجمة ناقصة بيرجع للعربي وبيطلع تحذير `[i18n] missing en` في الـ console أثناء التطوير. تبديل اللغة بيقلب `dir`/`lang` تلقائيًا (RTL/LTR) ويعيد رسم الصفحات.
- **أولوية اللغة:** اختيار المستخدم المحفوظ على حسابه ← اللغة اللي اختارها من شاشة الدخول ← لغة الوكالة الافتراضية (تتحدد من لوحة المنصة) ← العربية. زر التبديل في الشريط الجانبي وفي الإعدادات ← التفضيلات وفي شاشة الدخول.
- **اللي اتترجم:** كل الصفحات والنوافذ والقوائم والأخطاء اللي بترجع من السيرفر وتنبيهات النظام وأسماء الأدوار الافتراضية وتقرير CSV من لوحة القيادة، وفاتورة الـ PDF (`?lang=en|ar`، والافتراضي لغة الوكالة) مع اتجاه الصفحة والتواريخ.
- **الشاشات:** نافذة (Modal) موحدة بالستايل الجديد (Esc للإغلاق، قفل التمرير، تتحول لـ bottom-sheet على الموبايل)، وشبكات ثنائية العمود بتتكدس على الموبايل، والجداول بتتمرر أفقيًا داخل الكارت، وهوامش الصفحات أصغر على الموبايل/التابلت. اتفحصت كل الصفحات على عرض 375px: مفيش تمرير أفقي للصفحة.
- **حدود معروفة:** البيانات المخزنة (أسماء العملاء والخدمات المخصصة، فئات المصاريف، ملاحظات السجل الزمني القديمة) بتظهر زي ما اتكتبت ولا تُترجم. الإيميلات والإشعارات الخارجية لسه ما اتبنتش (المرحلة 3) وهتتبني ثنائية اللغة من البداية.

## المرحلة 3 — الإيميل + Webhooks + إعادة ترتيب الإعدادات
- **الإيميل:** nodemailer، إعدادات SMTP (منصة/وكالة) مع زر اختبار، قوالب (دعوة مستخدم، إعادة تعيين كلمة المرور، تذكير استحقاق، تنبيهات)، قائمة انتظار بإعادة محاولة وسجل إرسال.
- **Webhooks:** جداول endpoints/deliveries، توقيع HMAC-SHA256، إعادة محاولة بتأخير متزايد، أحداث: فاتورة اتعملت/اتدفعت/تأخرت، عميل جديد، تجديد قريب، دفعة تحصيل، إلخ.
- **صفحة الإعدادات:** تبويبات: الملف الشخصي، الأمان، التفضيلات، الوكالة، الأعضاء والأدوار، الإيميل، Webhooks، الإشعارات (وللـ Super Admin: إعدادات المنصة).

### حالة المرحلة 3 — ✅ منفّذة ومجرّبة على النسخة التجريبية
- **الإيميل:** SMTP للوكالة (يتخزن مشفّر) أو للمنصة، زر اختبار، سجل رسائل، إعادة محاولة تلقائية، قوالب عربي/إنجليزي، دعوة مستخدم بالإيميل، نسيت كلمة المرور/إعادة تعيين، تذكير دفع للعميل من التحصيل، إشعارات المديرين (سداد + ملخص متأخرات يومي).
- **Webhooks:** CRUD لكل وكالة، توقيع HMAC-SHA256، إعادة محاولة بتأخير متزايد، سجل تسليم + إعادة إرسال، زر اختبار، تجديد المفتاح، حماية من الروابط الداخلية (SSRF)، 7 أحداث، **GET/POST** مع رسائل جاهزة ونص مخصص وإعداد جاهز لـ **Telegram**.
- **الإعدادات:** تبويبات جديدة «البريد الإلكتروني» و«Webhooks» في صفحة الإعدادات، و«البريد (SMTP المنصة)» في إدارة المنصة.
- **التحقق:** `npm test` (47) + `npm run phase3` (54 فحص بسيرفر SMTP وسيرفر استقبال محليين) + `npm run isolation` (79) + `npm run audit` (292). التفاصيل التقنية في `docs/EMAIL-WEBHOOKS.md`.
- **مؤجّل:** حصر الإشعارات الأخرى (مثل تذكير تجديد للعميل نفسه) وقوالب إيميل قابلة للتعديل من الواجهة.

> 📌 خطوات النقل للإنتاج خطوة بخطوة (نسخة احتياطية، بصمة قبل/بعد، التحقق، الرجوع): **`docs/GO-LIVE.md`**.

## ملاحظات ومخاطر
- أكبر مخاطرة: عزل البيانات في `finance.js` (1000+ سطر SQL) — هيتغطّى باختبارات عزل مع وكالتين.
- العملة تفضل EGP لكل الوكالات حاليًا (تقارير كلها بتفلتر بالعملة).
- نسخة الإنتاج الحالية تتحوّل لأول وكالة بدون فقد بيانات: backup → migration → تحقق بأداة `npm run audit`.
- تفاصيل تتحدد وقت التنفيذ (افتراضات قابلة للتغيير): استعادة كلمة المرور عبر الإيميل، مدة الاحتفاظ بالسجلات (مقترح 12 شهر)، وحد المستخدمين الافتراضي للوكالة.
